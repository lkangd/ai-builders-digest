Quoting
steven hao@stevenkplus1
Bots are super cool and if you haven't used them yet, you absolutely must try them. Create a bot to manage a goal or a project that you'll work on across multiple sessions and days.

Some technical tidbits about the architecture and design:

Devin used to have a major UX problem: a session today doesn't remember exactly what happened in a session from a few days ago. It only has vague awareness of those previous sessions, and recalls only the nuggets of information that were explicitly persisted. This is because each new Devin was essentially an ephemeral clone of a base template. One symptom of this problem is that our users would reuse the same session instead of starting new ones, since they didn't want to lose context, and end up with tens or hundreds of PRs from a single session.

Bots almost completely solves this problem of context being lost between sessions, because now inter-session context is surfaced by default. Teams now create dedicated bots for different projects; while these different devins can talk to each other when necessary, they each have their own individual memory bank and goals. Each bot now has its own, long lived identity.

The transition from "Devin is a swarm of ephemeral agents" to "Devin is a collection of bots, each with their own persistent identity and memory" is changing how people use and prompt Devin. I see people investing much more in providing high level project context to their bot, and requiring fewer messages for each additional task since it already has a ton of background context on the project.

This is the most significant change to how Devin works since our original launch 2 years ago. And it in turn changes how you use Devin too: instead of delegating tasks, you should delegate goals and responsibilities to Devin.

It's crazy to think that all this happened because we changed how memories get persisted and retrieved. With each bot having its own memory bank, and a given org having hundreds or thousands of bots, we can now be much more aggressive in surfacing memories without worrying about polluting the agent's context with irrelevant memories. The even crazier part is that this is almost entirely an orchestration change, and that while model improvements played a role, we probably could've implemented this a year ago and observed similar effects.

Anyway -- we've come a long way from the retrieval and reranking strategies of 2024, and the result is Devin Bots -- probably the most ergonomic and futuristic UX for coding agents I've ever used.

一些关于架构和设计的技术细节：

Devin 曾经有一个很大的 UX 问题：今天的 session 记不住几天前那个 session 里到底发生了什么。它对那些先前的 session 只有模糊的意识，而且只回忆起被明确持久化的信息片段。这是因为每个新的 Devin 本质上都是一个基础模板的短暂克隆。这个问题的一个症状是，用户会反复使用同一个 session 而不是开新的，因为他们不想丢失上下文，结果一个 session 里会堆出几十甚至上百个 PR。

Bot 几乎彻底解决了跨 session 丢失上下文的问题，因为现在跨 session 的上下文默认就会被呈现出来。团队会为不同项目创建专用 bot；这些不同的 Devin 在必要时可以互相交流，但各自拥有独立的记忆库和目标。每个 bot 现在都有自己长期存在的身份。

从「Devin 是一群短暂的 agent」到「Devin 是一组 bot，每个都有持久身份和记忆」的转变，正在改变人们使用和 prompt Devin 的方式。我看到人们更愿意给自己的 bot 提供高层次的项目上下文，而每个后续任务需要的消息也更少，因为它已经有了大量项目背景。

这是自我们两年前首次发布以来，Devin 工作方式最重大的变化。它也会反过来改变你使用 Devin 的方式：你不应该再把任务委派给它，而应该把目标和职责委派给 Devin。

很难想象这一切只是因为我们改变了记忆被持久化和检索的方式。每个 bot 都有自己的记忆库，一个组织里可能有成百上千个 bot，我们现在可以更积极地呈现记忆，而不用担心用不相关的记忆污染 agent 的上下文。更疯狂的是，这几乎完全是一次编排层的变化，虽然模型改进也起了作用，但我们大概一年前就可以实现它，并观察到类似的效果。

总之，我们已经从 2024 年的检索和 reranking 策略走了很远，而结果就是 Devin Bots，大概是我用过的最符合人体工程学、也最有未来感的 coding agent UX。
